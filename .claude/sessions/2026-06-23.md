## First-day feature tour (coach-mark / spotlight overlay)

first app open. It dims the screen, cuts a morphing soft-cornered hole around a
target, traces it with a pulsing terracotta ring, and floats a Cozy card
("here's what this does"). Confetti fires on the final step.

## Feature tour v2 — two acts, with a real interactive prayer

Reworked the tour per user feedback into two acts:
- **Act 1 (interactive):** spotlight "Let's Pray Now", let the user tap through and actually pray (mood → choose prayer → read). The tour waits and resumes when they return home. Actually praying is the first "wow".
- **Act 2:** lock apps ("sealed until you pray, like you just did") → Bible → companion → **garden grows live** (the prayer they finished bumps it) → finish + confetti.

New order: welcome → pray(interactive) → lock(Profile) → bible → companion → garden → finish.

Implementation details:
- `TourStep` gained `interactive`, `hintKey`, `onReveal`.
- Interactive step: veil uses `IgnorePointer` so the tap reaches the real button; card drops Next and shows a "Tap to pray" hint; tour auto-advances via a route-stack poll (`ModalRoute.isCurrent`) with a 2-tick debounce.
- **Flow-return detection caveat:** the prayer selector closes *before* the reading screen opens, with an `await fetchPrayers()` gap that can hit the network (≤10s) on a cold cache. Mitigated by (a) prewarming `PrayerRepository().fetchPrayers()` when the tour begins, and (b) the 2-tick (~600ms) debounce. Not bulletproof if a cold network fetch exceeds the debounce — revisit with a real completion signal if it misfires.
- `GardenController.nurture()` added: animated single-prayer growth, called on the garden step's `onReveal`.
- Note: written-prayer `_finish` does NOT record stats (only a mood check-in) — there is no clean "prayer completed" observable, hence the navigation-based detection.

## Unlock challenge chooser (Quiz vs Prayer)

The app-unblock flow was a direct quiz (notif → `/prayer-learning` = PrayerLearningScreen, Read→Meditate→Remember→Complete, then UnlockDurationDialog → `UnlockTimerService.startUnlock` → `/main`). Added a choice step in front.

New flow: notif/deeplink/auto-nav → **`UnlockChooserScreen`** (`/unlock-chooser`):
- **Quiz** → existing PrayerLearningScreen (unchanged, self-unlocks).
- **Prayer** → expands to **Audio** / **Text** → ask mood now (`showCozyMoodCheckIn`) → `MoodPrayerMatch.recommend` (audio filters to audio-capable prayers) → open `PrayerPlayerScreen` / `CozyWrittenPrayerScreen` in unlock mode → on completion run the shared `finishUnlock` (UnlockDurationDialog → record → `UnlockTimerService.startUnlock` → `/main`).
- **"Remember my choice"** checkbox shown from the **2nd** unlock onward (gated by a persisted `unlock_event_count`); remembered method skips the chooser. **Editable in Profile** → Settings → "Unlock method" (Ask every time / Quiz / Prayer·Audio / Prayer·Read).

Decisions (user): prayer unlock asks the same duration dialog as the quiz; mood is asked fresh at each unlock.

New/changed:
- `UnlockFlowService` (enum `UnlockMethod`, remembered-choice + event-count persistence, `start`/`startQuiz`/`startPrayer`/`finishUnlock`).
- `UnlockChooserScreen` (Cozy).
- `PrayerPlayerScreen` + `CozyWrittenPrayerScreen` gained optional `onCompleted` (runs after the post-prayer mood check-in; unlock mode).
- 5 nav sites redirected `prayerLearning` → `unlockChooser` (deep_link, notification_navigation, local_notification, auto_navigation×2). Route `/unlock-chooser` registered.
- Profile `_UnlockMethodTile` setting; `unlock_*` strings (EN+FR).
- `flutter analyze` clean.

Note: the LIVE unlock path is `UnlockTimerService.startUnlock(duration:)` (timed temporary unlock), NOT the dead `UnlockController._handleSuccessfulUnlock`/`stopBlocking()` (that's the unused `UnlockScreen`).

## PostHog: ROOT-CAUSE fix — only onboarding events were reaching PostHog

User saw only onboarding_* events in PostHog (no unlock/prayer/bible/tour). Diagnosed:
- The onboarding module calls `Posthog().capture()` DIRECTLY → bypasses the gate → shows up.
- EVERYTHING else uses `events.trackCustom`, which early-returns on `!_canTrackEvent(name)`. `canTrackEvent` requires `consentStatus == ConsentStatus.granted`, but the default is `ConsentStatus.pending` and NOTHING ever granted it (the grant block in `PostHogService.init` was commented out). → every custom event (existing `unlock_successful`, `prayer_session_*`, `lock_challenge_*` AND all the new instrumentation) was silently dropped.

Fixes (analytics infra, none in agent files):
1. `posthog_service.dart init()` — default-grant consent once when `pending` (respects an explicit later opt-out). This retroactively activates ALL custom analytics.
2. `event_tracking_module.dart _sendEvent()` — drop null-valued props before `Posthog().capture` (`null as Object` threw and silently dropped any event with an optional prop; our spec uses many nullable props).
3. `main.dart` — after PostHog init, `users.identify(userId: supabase anon user.id, properties: {user_since: user.createdAt})` so events attach to a stable person across launches + "user since" = account creation (user request).
